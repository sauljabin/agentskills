Design document

Publish order events with a transactional outbox

Every committed order produces exactly one OrderPlaced event, even when Kafka is down at checkout time.

Overview

Orders API saves an order in PostgreSQL and then publishes OrderPlaced to Kafka as a second step. When that second step fails, the order exists but Billing and Shipping never hear about it; in September this happened to 1,214 orders. This design writes the event to an outbox table in the same transaction as the order, and Debezium copies it to Kafka from the database log, so an event exists if and only if its order does. The cost is a new Kafka Connect deployment and duplicate events that every consumer must drop.

Reviewers

Two answers block the rollout: who runs Kafka Connect (Q1) and whether the database reboot fits the 2026-11-24 maintenance window (Q3).

Problem

The commit and the publish are two separate steps, a dual write, and nothing retries the second one after the first succeeds. Order 84121 shows what happens when a broker restarts during checkout:

Retrying the publish does not close the gap: if the pod dies between the commit and the retry, the event is still lost.

Goals

  • Every committed order produces its event, and no event exists for an order that rolled back.
  • 99% of events reach Kafka within 2 s of the commit.
  • Orders API keeps accepting orders while Kafka is down.
  • Consumers change how they read events, not what they do with them.

Non-goals

  • Event sourcing: orders stay rows in PostgreSQL.
  • Exactly-once delivery end to end. Consumers drop duplicates instead (D4).
  • Events for payments and refunds (P1).
  • Events for orders created before the rollout.

The order and its event commit together

Orders API inserts the event into an outbox table in the same transaction as the order and deletes it before the commit. The insert stays in the database log, so the event exists only if the order committed.

How it works

Architecture

Orders API stops talking to Kafka. It writes to PostgreSQL only, and Debezium turns the database log into events. Hover a box or an arrow for details, or a step below to follow it in the diagram.

  1. Checkout sends POST /orders to Orders API.
  2. Orders API inserts the order and its event, deletes the event row, and commits, all in one transaction.
  3. Debezium reads the outbox insert from the WAL, even though the row is already gone from the table.
  4. Debezium publishes the event to orders.events.v1 with the order ID as the key.
  5. Billing and Shipping consume the event and skip IDs they have already processed.

The order and its event commit together

D1 The outbox table holds the event in the shape it will have in Kafka. Debezium needs only the insert, which is already in the WAL when the transaction commits, so Orders API deletes the row in the same transaction and the table stays empty.

If anything in placeOrder throws, the transaction rolls back and the WAL never contains a committed insert, so no event is published.

Debezium copies events from the WAL

D2 The connector reads the outbox table through logical replication and keeps its position in the replication slot debezium_orders. The outbox event router turns each insert into a Kafka record and ignores the deletes.

Turning on logical replication reboots the database

RDS applies rds.logical_replication = 1 only after a reboot. On staging the Multi-AZ failover rejected writes for 95 s. The reboot is step 1 of the rollout and waits for Q3.

One topic, keyed by order ID

D3 Kafka keeps records with the same key in one partition, in the order they were written. Keying by order ID means a future OrderCancelled can never overtake its OrderPlaced.

Strengths and weaknesses

Strengths

  • An event exists if and only if its order committed: no lost events and no events for rolled-back orders (D1).
  • Orders API never calls Kafka, so a Kafka outage neither fails nor slows checkout (F3).
  • No polling: zero extra queries on the orders database, and 380 ms p99 from commit to topic on staging (D2).
  • The events of one order arrive in order, because they share a key (D3).
  • The outbox table stays empty, so there is no cleanup job and no table bloat.

Weaknesses

  • Kafka Connect is a new deployment to run, upgrade and watch (Q1).
  • While the connector is stopped, PostgreSQL keeps the WAL. At 50 GB it drops the slot and the unpublished events are lost (F2, G3).
  • Duplicates are normal after connector restarts, so every consumer must drop them (D4, G1).
  • Turning on logical replication needs a database reboot: 95 s of rejected writes on staging.
  • Pending events are not visible in SQL, because the rows are deleted at once. You read the topic instead (runbook).

A1

Dual write with retries

Rejected

Keep today's flow and retry the publish 5 times with backoff.

Why not
It shrinks the gap but keeps it: a pod restart between the commit and a successful retry still loses the event.
Better if
A lost event were cheap to fix, for example a cache refresh that the next event repairs.
A2

Listen to yourself

Rejected

Orders API publishes the event first and builds the orders table by consuming its own topic.

Why not
It rewrites how Orders API stores state, and a new order is not readable until the API consumes its own event, which breaks the checkout confirmation page.
Better if
We were building the service from scratch around events.

Rejected in v0.2

Rollout and rollback

D6 The old producer keeps publishing to orders until consumers have run on the new topic for 14 days, so every step before the last one can be undone.

  1. Set rds.logical_replication = 1 and max_slot_wal_keep_size = 51200 (50 GB) in the parameter group, and reboot in the maintenance window (Q3).
  2. Deploy Orders API with orders.outbox.enabled=true. The old producer keeps publishing to orders.
  3. Create the orders-outbox connector. Events start to flow to orders.events.v1.
  4. Shadow run: the daily comparison must find 0 missing events for 7 days in a row.
  5. Move Billing to orders.events.v1, then Shipping once G1 is fixed.
  6. After 14 days on the new topic, remove the old producer and delete the orders topic.

Rollback

Before step 5, turn the flag off and delete the connector; nothing downstream has changed. During step 5, point the consumer back at orders and reset its offset to the switch time. After step 6 there is no rollback, only fixes forward.

Runbook

The connector task moves between these states. Only RUNNING publishes events:

Check the connector, and restart its task when it is FAILED:

curl -s https://connect.internal.example.com/connectors/orders-outbox/status | jq '.tasks[].state'
curl -s -X POST https://connect.internal.example.com/connectors/orders-outbox/tasks/0/restart

See how much WAL the slot is holding:

SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots
WHERE slot_name = 'debezium_orders';

Read the last 5 events of each partition, since pending events are not in the outbox table:

kcat -b kafka.internal.example.com:9092 -t orders.events.v1 -C -o -5 -e -f 'key=%k %s\n'

Known gaps

Problems this design does not solve yet. Each one has a proposed fix and an owner.

G1

Shipping does not drop duplicates

Blocks step 5

Shipping creates one shipment per OrderPlaced it reads. After a connector restart (F5), order 84121 would ship twice.

Options
A processed_events table, as in Billing; or a unique constraint on shipments(order_id).
Proposal
The unique constraint: one order has one shipment, and the constraint also protects against bugs outside this design.
Owner
Luis Ortega (Shipping)
G2

Nothing checks event schema changes

Before a third consumer

Renaming total_cents to total passes every Orders API test and breaks Billing in production.

Options
JSON Schema files in the repository with a compatibility check in CI; or Avro with a schema registry (P2).
Proposal
JSON Schema in CI now. It needs no new infrastructure and keeps D5.
Owner
Ana Ruiz (Orders)
G3

No way to rebuild events after the slot is dropped

Before step 6

If F2 reaches 50 GB, the events in that window are gone: the outbox rows were deleted, and the old producer is the only other copy until step 6.

Options
Keep outbox rows for 7 days and delete them with a job; or derive event_id from the order ID and event type, and rebuild missing events from the orders table with a backfill script.
Proposal
The backfill script with derived IDs: consumers drop any event that was not lost, so it is safe to over-publish. This changes how D5 creates event_id.
Owner
Ana Ruiz (Orders)

Glossary

CDC
Change data capture: reading a database's changes from its log as a stream, instead of querying its tables.
Dual write
Writing the same fact to two systems in two separate steps, such as a database commit followed by a Kafka publish. If the second step fails, the two systems disagree.
Idempotent consumer
A consumer that gives the same result when it processes the same event twice, usually by remembering the event IDs it has handled.
Logical replication
PostgreSQL's way of streaming row changes from the WAL to an outside reader. Debezium uses it with the pgoutput plugin, which is how it does CDC.
LSN
Log sequence number: a position in the WAL, such as 0/1A2B. Debezium saves the last LSN it published and resumes from there.
Outbox
A table where a service writes events in the same transaction as its data, so the events commit or roll back together with it.
Replication slot
A named position in PostgreSQL that keeps WAL until its reader confirms it. Ours is debezium_orders.
WAL
Write-ahead log: PostgreSQL's record of every change, written before the change reaches the tables.
